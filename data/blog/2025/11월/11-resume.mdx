## Waiker Widget Module

**멀티 인스턴스 위젯 시스템 개발**

Turborepo 기반 모노레포 아키텍처를 설계하여 재사용 가능한 10개 이상의 공유 패키지(UI, API, 유틸리티 등)를 구축하였습니다. 동일 페이지에서 여러 위젯이 충돌 없이 동작하도록 Scoped Context 패턴을 적용하여 CSS, 상태, DOM을 완전히 격리하는 시스템을 구현하였으며, CDN 배포 및 Import Map 기반 마이크로 프론트엔드 아키텍처를 통해 독립적인 배포 파이프라인을 구성하였습니다.

**기술:** React, TypeScript, Zustand, Turborepo, PNPM Workspace, PostCSS, Tailwind CSS

## 1. 아키텍처 & 설계 (Architecture)

### 모듈형 플랫폼 설계

서비스 소개  
Turborepo + PNPM Workspace 기반의 모던 모노레포 구조  
이 프로젝트의 Scoped Context 패턴은 여러 위젯 인스턴스가 같은 페이지에 공존할 때 각각 독립적인 상태와 스타일을 유지하기 위한 아키텍처 패턴입니다.

CSS 격리

- 빌드 시 모든 CSS 셀렉터를 .waiker-widget-container 안으로 스코프
- :root, html, body 등의 글로벌 셀렉터를 컨테이너로 치환
- data-theme 속성을 사용해 테마 격리

```css
/* 빌드 전 */
.button {
  color: red;
}

/* 빌드 후 */
.waiker-widget-container .button {
  color: red;
}
```

Portal 스코프 격리  
핵심 아이디어:

- 앵커 기반 탐색: 현재 컴포넌트의 위치(anchorRef)에서 시작
- closest() 사용: 가장 가까운 .waiker-widget-container를 찾음
- Portal 생성: 찾은 컨테이너 내부로 Portal 생성

상태 스코프 격리 (Zustand + React Context)  
아키텍처 특징:

- Zustand Vanilla Store + React Context 조합
- createStore(): 프레임워크 독립적인 순수 상태 스토어
- React.createContext(): 스토어 인스턴스를 컴포넌트 트리에 주입
- 각 위젯 인스턴스마다 독립적인 스토어 인스턴스 생성

이 패턴이 특히 유용한 경우

- 멀티 테넌트 위젯: 같은 페이지에 여러 위젯 인스턴스
- 써드파티 임베드: 호스트 페이지와의 스타일/상태 충돌 방지
- 마이크로 프론트엔드: 독립 배포 가능한 모듈화된 UI

금융 위젯을 여러 플랫폼(자사 서비스, B2B 파트너사)에 배포해야 하는데, NPM 패키지 하나로는 한계가 있었습니다. 그래서 Monorepo + 멀티 빌드 타겟 아키텍처를 설계해서, 같은 코드베이스에서 SDK와 CDN ESM 두 가지 배포 형태를 동시에 지원하도록 구축했습니다. 결과적으로 번들 크기 60% 절감, 독립 배포 주기 단축, TypeScript 완벽 지원을 달성했습니다.

**Q1.** iframe, CDN, SDK 기반 동적 모듈 로딩 아키텍처를 구축하셨는데, 각 방식의 장단점과 어떤 기준으로 선택하셨나요?
처음 이 서비스를 설계할때는 고객사쪽에서 쉽게 사용할 수 있는 형태로 제공하기위해서 iframe 형태만 고려했었습니다.
아무래도 가장 고객사쪽에서 추가적인 개발 없이 간단하게 가져다 사용할 수 있는 형태라 이렇게 계획을 했었는데
해당 위젯을 내부 서비스에서도 사용하려고 하다보니 한계가 있었습니다. postMessage 를 통해서 데이터를 주고받도록 만들긴 했었는데
단순하게 완성된 위젯을 제공하려고했던것에서 벗어나 커스텀이나 다양한 호출 방식을 고려하다보니 내부 코드가 지저분해지고 관리의 문제가 계속 발생했습니다.
그래서 내부 서비스에서의 호출 뿐만아니라 다양한 고객의 니즈도 확장해서 반영할 수 있도록 cdn 과 SDK 형태로도 제공할 수 있는 형태로 만들게 되었습니다.

## 🏗️ 구현된 3가지 아키텍처

### 1️⃣ **NPM SDK 방식** (`@waiker-inc/widget`)

**구현 방식:**

- GitHub Packages에 배포되는 NPM 패키지
- React 컴포넌트로 직접 임포트하여 사용
- Peer dependencies로 React, Zustand 등 공유

**장점:**

- ✅ 강력한 타입 안전성 (TypeScript 지원)
- ✅ IDE 자동완성 및 인텔리센스
- ✅ 빠른 개발 속도 (npm install만)
- ✅ 버전 관리 용이 (package.json으로 명시적 관리)
- ✅ 빌드 타임 최적화 (Tree shaking, Code splitting)
- ✅ 호스트 앱과 의존성 공유로 번들 크기 최소화

**단점:**

- ❌ 호스트 앱 재배포 필요 (위젯 업데이트 시)
- ❌ 빌드 프로세스 통합 필요
- ❌ React 버전 충돌 가능성
- ❌ 실시간 업데이트 불가

---

### 2️⃣ **CDN + Import Map 방식**

**구현 방식:**

- ES Module로 CDN에 배포
- ES Module Shims + Import Map으로 동적 로딩
- 각 위젯을 독립적인 모듈로 분리

**장점:**

- ✅ 실시간 업데이트 가능 (호스트 앱 재배포 불필요)
- ✅ 독립적인 배포 파이프라인
- ✅ 버전별 캐싱 전략 (CDN 레벨)
- ✅ 필요한 위젯만 온디맨드 로딩 (대역폭 절약)
- ✅ 다중 버전 동시 운영 가능
- ✅ 호스트 앱과 기술 스택 독립성

**단점:**

- ❌ 초기 로딩 시간 증가 (네트워크 요청)
- ❌ 브라우저 Import Map 지원 필요 (폴리필 필요)
- ❌ 디버깅 어려움 (소스맵 관리)
- ❌ 타입 안전성 약화
- ❌ CDN 장애 시 위젯 전체 다운

---

### 3️⃣ **Scoped Context (iframe 대안) 방식**

**구현 방식:**

- 위 1, 2번 방식에 공통으로 적용되는 격리 패턴
- CSS Scoping + Portal + 독립 상태 관리

**iframe 대비 장점:**

- ✅ DOM 완전 통합 (검색엔진 최적화 가능)
- ✅ 부모-자식 간 통신 간편 (postMessage 불필요)
- ✅ 반응형 레이아웃 용이
- ✅ 성능 우수 (별도 렌더링 컨텍스트 불필요)
- ✅ 접근성 향상 (단일 DOM 트리)

**iframe 대비 단점:**

- ❌ 완벽한 격리는 아님 (CSS 변수, 글로벌 이벤트 등)
- ❌ 보안 수준 약함 (Same-origin에서만 가능)

## 🎯 선택 기준 (실무 관점)

### **NPM SDK 방식을 선택한 경우:**

- **내부 프로젝트** (자사 웹사이트에 통합)
- **긴밀한 통합** 필요 (Redux 공유, 라우팅 통합 등)
- **타입 안전성** 중요
- **빌드 최적화** 우선
- **버전 동기화** 가능

**적용 사례:**

- Waiker 공식 웹사이트
- 내부 대시보드 시스템

---

### **CDN + Import Map 방식을 선택한 경우:**

- **외부 고객사 제공** (B2B SaaS)
- **실시간 업데이트** 필요 (버그 수정 즉시 반영)
- **다양한 버전 지원** 필요
- **호스트 앱 재배포 불가** 환경
- **마이크로 프론트엔드** 아키텍처

**적용 사례:**

- 증권사 웹사이트 임베드
- 뉴스 포털 위젯
- 금융 플랫폼 통합

---

### **선택 결정 트리:**

```
고객사 통합인가?
├─ YES → 기술 스택 공유 가능?
│   ├─ YES → NPM SDK 방식
│   └─ NO  → CDN + Import Map 방식
│
└─ NO (내부) → 실시간 업데이트 필요?
    ├─ YES → CDN + Import Map 방식
    └─ NO  → NPM SDK 방식
```

## 🎤 이력서 작성 예시

**"멀티 채널 배포를 위한 하이브리드 위젯 아키텍처 설계"**

NPM SDK와 CDN Import Map 방식의 이중 배포 전략을 구축하여 다양한 고객 환경에 대응했습니다. 내부 통합을 위한 NPM 패키지는 타입 안전성과 빌드 최적화에 중점을 두었고, 외부 고객사 대응을 위한 CDN 방식은 ES Module Shims 기반 동적 로딩으로 실시간 업데이트를 가능하게 했습니다. iframe의 격리 장점을 유지하면서도 DOM 통합과 SEO를 보장하는 Scoped Context 패턴을 설계하여 양쪽 방식에 공통으로 적용했습니다. 이를 통해 내부 프로젝트는 50KB 번들로 최적화하고, 외부 임베드는 호스트 재배포 없이 실시간 업데이트를 달성했습니다.
